One of the less glamorous parts of maintaining a software project is release management. Projects vary, of course, but a release might include creating application bundles; signing artifacts; pushing to "stores" like Maven Central, Homebrew, sdkman, etc; creating GitHub releases; announcing the release; and maybe many, many others. The more complex a project's release requirements are, the more opportunities for error there are. A tool exists, though, to help streamline this process, JReleaser. In this post, we'll take a quick look at what the tool is and see a fairly simple configuration to help get you started.

Quoting from the https://jreleaser.org/[JReleaser site]:

[quote, https://jreleaser.org/]
____
JReleaser is a release automation tool. Its goal is to simplify creating releases and publishing artifacts to multiple package managers while providing customizable options. However, you may also use it with projects that do not require publishing binary assets. The tool can be used to create Git releases (tag, changelog, assets), announce releases, assemble additional binaries and files to be published via package managers. JReleaser supports any kind of project regardless of its source language (Java, Go, Node, Rust, Perl, Python, C/C++, C#, Elixir, Haskell, etc), although it provides additional benefits to Java-based projects.
____

To learn how to use JReleaser, we'll develop a configuration to create a GitHub release, publish it to Maven Central, as well as publish a JBang script to make our demo app easy to access.

== The Basic Project

To avoid too much noise, we're just going to fork a https://tamboui.dev/docs/main/demos-toolkit.html#new-year[demo app] from TamboUI. The app itself is not important, so we'll skip the details here. You can, of course, see the full app in all its glory in the https://github.com/jasondlee/jreleaser-demo[git repo].

== Preparing the POM

Before we can worry too much about the JReleaser config, we need to make sure the POM has certain functionality configured. In a real app or library, you probably have this done already, but we don't for this app, so we need to add it. Doing so highlights the requirement anyway.

To deploy to Central, we're going to need source and javadoc archives, otherwise the deployer will complain (there might be a way to silence that, but it seems like a good thing to do regardless). To do that, we'll configure a couple of plugins, `maven-source-plugin` and `maven-javadoc-plugin`. For large projects, these might take time I don't want to spend while developing, so we'll put these in a profile so they're enabled only when needed:

[source,xml]
----
<profiles>
    <profile>
        <id>release</id>
        <build>
            <plugins>
                <plugin>
                    <groupId>org.apache.maven.plugins</groupId>
                    <artifactId>maven-source-plugin</artifactId>
                    <executions>
                        <execution>
                            <id>attach-sources</id>
                            <phase>verify</phase>
                            <goals>
                                <goal>jar-no-fork</goal>
                            </goals>
                        </execution>
                    </executions>
                </plugin>
                <plugin>
                    <groupId>org.apache.maven.plugins</groupId>
                    <artifactId>maven-javadoc-plugin</artifactId>
                    <executions>
                        <execution>
                            <id>attach-javadocs</id>
                            <phase>verify</phase>
                            <goals>
                                <goal>jar</goal>
                            </goals>
                        </execution>
                    </executions>
                </plugin>
            </plugins>
        </build>
    </profile>
</profiles>
----

JReleaser also seems to want a local "deploy" directory to work against, so we'll configure the `maven-deploy-plugin`:

[source,xml]
----
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-deploy-plugin</artifactId>
    <version>3.1.4</version>
    <configuration>
        <altDeploymentRepository>
            local::file://${project.build.directory}/staging-deploy
        </altDeploymentRepository>
    </configuration>
</plugin>
----

== JReleaser Configuration

Now we're ready to configure JReleaser. You have at least a couple of options. You can configure it via an external YAML file or via your Maven POM. I tend to prefer the POM file as it requires less duplication of information (project version, authors, description, etc), and doesn't require the installation of another tool. It does, though, bloat your POM some, so keep that in mind when making your choice. For this project, we'll add this plugin configuration to our `release` profile:

[source,xml]
----
<plugin>
    <groupId>org.jreleaser</groupId>
    <artifactId>jreleaser-maven-plugin</artifactId>
    <version>1.25.0</version>
    <inherited>false</inherited>
    <configuration>
        <jreleaser>
            <project>
                <inceptionYear>2026</inceptionYear>
                <languages>
                    <java>
                        <mainClass>${mainClass}</mainClass>
                    </java>
                </languages>
            </project>
            <release>
                <github>
                    <owner>jasondlee</owner>
                    <overwrite>true</overwrite>
                    <branch>master</branch>
                    <changelog>
                        <formatted>ALWAYS</formatted>
                        <preset>conventional-commits</preset>
                        <contributors>
                            <enabled>true</enabled>
                        </contributors>
                    </changelog>
                </github>
            </release>
            <distributions>
                <jreleaser-demo>
                    <type>SINGLE_JAR</type>
                    <artifacts>
                        <artifact>
                            <path>${project.build.directory}/${project.build.finalName}.jar</path>
                        </artifact>
                    </artifacts>
                    <jbang>
                        <active>ALWAYS</active>
                    </jbang>
                </jreleaser-demo>
            </distributions>
            <signing>
                <pgp>
                    <active>ALWAYS</active>
                    <armored>true</armored>
                </pgp>
            </signing>
            <deploy>
                <maven>
                    <mavenCentral>
                        <sonatype>
                            <active>ALWAYS</active>
                            <url>https://central.sonatype.com/api/v1/publisher</url>
                            <checksums>true</checksums>
                            <applyMavenCentralRules>true</applyMavenCentralRules>
                            <stage>UPLOAD</stage>
                            <stagingRepositories>
                                <stagingRepository>${project.build.directory}/staging-deploy</stagingRepository>
                            </stagingRepositories>
                        </sonatype>
                    </mavenCentral>
                </maven>
            </deploy>
        </jreleaser>
    </configuration>
</plugin>
----

The configuration model, regardless of format, is quite large, so I can't cover it all here, but I'll try to give a brief overview of each section used here.

=== Section: <project>

This, obviously, defines the project. Most information here will be pulled straight from the POM (N.B., with `jreleaser.yaml`, this section would be much more verbose, repeating a fair bit of project metadata). If you'd like to override information for whatever reason, you may do so here.

For full details on what options are available, see the `Project` model https://github.com/jreleaser/jreleaser/blob/main/api/jreleaser-model-api/src/main/java/org/jreleaser/model/api/project/Project.java[here].

=== Section: <release>

In this section, we describe our GitHub release. The `owner` can be inferred from the repository owner, but I've specified it here from clarity, which will also enable releases from forks should you choose to do so. We can also configure whether to replace existing releases (should you need to correct an error, for example), as well as how the changelog should look.

Full model details, see https://github.com/jreleaser/jreleaser/blob/main/api/jreleaser-model-api/src/main/java/org/jreleaser/model/api/release/Release.java[here].

=== Section: <distributions>

In this section, we'll define our distributions. This section is a map, so the top-level elements in this section will be the entry keys. Our only distribution is a single jar, which is just the artifact that Maven builds.

We have also specified a JBang deployment, and this might be one of my favorite features. When JReleaser creates the release, it will:

- Create a file called $ARTIFACT.java in a Git repository, https://github.com/jreleaser/jreleaser/blob/v1.25.0/core/jreleaser-model-impl/src/main/java/org/jreleaser/model/internal/packagers/JbangPackager.java#L257[jbang-catalog], owned by `owner`.
- This JBang script will refer to your project's artifact by, for example, the Maven Central GAV or a jitpack URL pointing at your project's source repository.
- Add an alias to `$JBANG_REPO/jbang-catalog.json` to publish the script.


=== Section: <signing>

This section configures signing globally for the JReleaser project. Some deployers (e.g., Maven Central) require signing, and configuring this here means we don't need to configure it for each deployer that needs it.

=== Section: <deploy>

Here we can define where we want the project artifacts deployed (Central, Nexus, Gitlab, etc). The configuration seems a bit odd here. The model looks like this:

[source,xml]
----
<deploy>
    <maven>
        <mavenCentral>
            <sonatype> <!-- You can have multiple Maven deployments, keyed by this name -->
                <active>ALWAYS</active>
                <url>https://central.sonatype.com/api/v1/publisher</url>
                <stage>UPLOAD</stage>
                <stagingRepositories>${project.build.directory}/staging-deploy</stagingRepositories>
            </sonatype>
        </mavenCentral>
    </maven>
</deploy>
----

Most of this is pretty straightforward, but one option I'd like to call out and stress is `<stage>`. The default value is `FULL`, which means JReleaser will upload and then publish your artifact whether you want to or not. With `UPLOAD`, you have to manually publish it from the Maven Central dashboard, which I prefer as a safeguard, since you can't unpublish from Maven Central. Assuming you're not running this from a GitHub Action, I like the safety net this provides.

== Secrets Config

Depending on how you want to run JReleaser (i.e., from your local workstation via the command line or from a GitHub Action), you're going to need to provide secrets to JReleaser somehow. For local runs, you can define environment variables, or use `$HOME/.jreleaser/config.properties`. That file might look something like this:

[source,properties]
----
JRELEASER_MAVENCENTRAL_STAGE=UPLOAD
JRELEASER_DEPLOY_MAVEN_MAVENCENTRAL_USERNAME=...
JRELEASER_DEPLOY_MAVEN_MAVENCENTRAL_PASSWORD=...
JRELEASER_DEPLOY_MAVEN_MAVENCENTRAL_TOKEN=...
JRELEASER_GITHUB_TOKEN=...
JRELEASER_GPG_PASSPHRASE=...
JRELEASER_GPG_SECRET_KEY=...
JRELEASER_GPG_PUBLIC_KEY=...
----

I'll leave it as an exercise for the reader to figure out how to get those, but their values should be pretty obvious. The only catch is the GPG keys, which seem to need to be the ascii-armored keys themselves. I've read through the JReleaser source a bit and saw nothing to suggest otherwise.

Once that looks right, you're almost ready to release. Maven Central does not allow `SNAPSHOT` deployments, so we need to set the version correctly, then we can deploy.

[source,bash]
----
$ mvn versions:set -DnewVersion=1.0.0
$ mvn -Prelease clean deploy jreleaser:full-release
----

After a brief wait, depending on the size of your project, you should have a pending release in Maven Central, a published release on GitHub, and a JBang script ready to call:

- https://central.sonatype.com/publishing
- https://github.com/jasondlee/jreleaser-demo/releases/tag/v0.0.1
- https://github.com/jasondlee/jbang-catalog/blob/master/jbang-catalog.json
  - https://github.com/jasondlee/jbang-catalog/blob/master/jreleaser_demo.java

Assuming you've added my JBang catalog to your local config (which is a HUGE assumption), you can now run the application:

[source,bash]
----
$ jbang jreleaser-demo@jasondlee
----

There is one last step I'd like to note. If you use the Maven Release Plugin, you're likely chafing a bit at setting the version manually, etc. Fortunately, this is pretty easy to fix. We just need to tweak the JRelease Maven plugin config a bit to tell it to execute when deploying:

[source,xml]
----
<executions>
    <execution>
        <id>release</id>
        <phase>deploy</phase>
        <goals>
            <goal>full-release</goal>
        </goals>
    </execution>
</executions>
----

Now, JReleaser will participate in the deployment process orchestrated by the Release plugin:

[source,bash]
----
$ mvn release:prepare
$ mvn -Prelease release:perform
----
